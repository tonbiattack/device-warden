# AI連携の実環境検証手順

この手順はIssue #15向けです。**実行結果を保証するものではありません。** 実機を使う前に作業者と使用状況を確認し、Device Wardenを通じて確保してください。管理外の直接ADB利用は検出できません。

## 準備

- Windows上でBrokerとトレイを起動し、ADB接続済みでAI利用許可されたテスト端末を2台用意する。片方はエミュレーターでもよい。
- 実際のシリアル、リースID、トークン、セッション名、ローカルパスを共有ログやIssueに貼らない。
- 端末で実行するのは読み取り専用操作に限定する。作業後は取得したリースを明示的に解放する。

## OpenCode

1. 別々の2セッションで `device_warden` の `list` を呼び、別々の端末を `claim` する。
2. GUIの詳細画面で、それぞれ実際のセッションID・タイトル・プロジェクトと一致することを確認する。
3. 各リースに対して `adb` アクションで `shell getprop ro.build.version.sdk` を実行する。直接 `adb` は実行しない。
4. 各セッションで `release` し、一覧で未確保に戻ることを確認する。
5. テスト専用Brokerで停止・heartbeat失敗を再現し、次のツール呼び出しが失敗して直接ADBへ切り替わらないことを確認する。

## Codex / Command Code

各ツールで `device-warden with-device --tool <ツール名> -- shell getprop ro.build.version.sdk` を実行する。終了時のリースと監査履歴を確認する。並列実行では同じ端末の二重確保がないこと、利用可能端末がない場合はADBを実行せず失敗することを確認する。異常時はリースを保持するため、ログに出たリースIDを公開せず、安全を確認してから解放する。

## 実施記録

2026-11-15、このリポジトリのOpenCodeセッションで、実機を1台 `claim` → `heartbeat` → 読み取り専用 `adb` → `release` まで確認した。セッションID・タイトル・プロジェクトがGUIに反映され、テスト中の35秒間隔でheartbeatが更新されることも確認している。CLIの確保・解放と、Broker再起動・接続断でリースが要確認として保持される動作は、単体テストと実環境の両方で確認した。

### 2026-11-21 追記（Command Code と2セッション同時確保）

エミュレーター（Android、`sdk_gphone64_x86_64`）を接続した環境で、残っていた項目のうち2つを実施した。

**Command Code（実ツール、v1.91.1）**

`command-code -p` から `device-warden with-device --tool "Command Code" -- shell getprop ro.product.model` を実行し、`sdk_gphone64_x86_64` を取得した。監査履歴に `claim` → `release` が `tool: "Command Code"` として記録され、確保・ADB実行・解放が一巡したことを確認した。

**Broker停止時に直接ADBへ流れないこと**

Brokerを停止した状態で同じコマンドを実行し、CLI・Command Code の双方が `Brokerに接続できません。device-warden-brokerを起動してください。` で終了コード1を返し、ADBを実行しないことを確認した。fail closed になっている。

**2セッションによる同時確保**

異なるセッションIDで `claim` を実行した。1つ目が `emulator-5554` を確保し、2つ目は `条件に合う空き端末がありません` で拒否された。`list` の確保者欄に `OpenCode` とセッションIDが表示されることも確認した。端末が1台のため「片方だけ成功」が正しい結果であり、二重確保は起きていない。
